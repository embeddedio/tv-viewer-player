# Repository Guidelines

## Project Structure & Module Organization
The Expo/React Native TV app lives at the repository root. Main entry points are `App.tsx`, shared display logic is in `components/`, and layout definitions are in `layouts.ts`. Native projects generated by Expo are in `android/` and `ios/`. Static artwork and TV banner assets are in `assets/images/`.

The embedded Node server lives in `server/`. Runtime data is kept in `server/data/`, uploads in `server/uploads/`, and reusable server helpers in `server/lib/`. The admin dashboard is a separate Vite app under `server/views/`. After server changes, sync them into `nodejs-assets/nodejs-project/`, which is the packaged Node.js Mobile runtime copy used by the native app.

## Build, Test, and Development Commands
- `npm start`: start Expo in TV mode (`EXPO_TV=1 expo start`).
- `npm run android`: build and run the Android TV native app.
- `npm run ios`: build and run the Apple TV/iOS native app.
- `npm run web`: launch the Expo web target for quick UI checks.
- `npm run prebuild:tv`: regenerate native projects with TV-specific Expo config.
- `npm run build:admin`: build the Vite admin UI in `server/views/`.
- `npm run sync:server`: copy `server/` changes into `nodejs-assets/nodejs-project/`.

Example: after editing `server/lib/config.js`, run `npm run sync:server` before testing on device.

## Coding Style & Naming Conventions
Use TypeScript for app code and keep React components in PascalCase files such as `components/TickerMarquee.tsx`. Prefer functional components and hooks. Match the existing style: double quotes in TS/TSX, semicolons, and 2-space indentation in app files. The embedded server uses CommonJS with single quotes.

Keep module names descriptive and aligned with feature purpose. Use camelCase for variables/functions and UPPER_SNAKE_CASE for shared constants.

## Testing Guidelines
There is no first-party automated test suite yet. Validate changes manually with `npm start`, then test the relevant native target with `npm run android` or `npm run ios`. For admin UI changes, also run `npm run build:admin`. If you add tests later, place them beside the feature as `*.test.ts` or `*.test.tsx`.

## Commit & Pull Request Guidelines
Git history currently only shows `init commit`, so there is no strong convention to inherit. Use short, imperative commit subjects such as `Add layout rotation fallback` and keep unrelated changes out of the same commit.

Pull requests should summarize user-visible behavior, list manual verification steps, and include screenshots for admin UI or signage layout changes. Call out any required `prebuild` or `sync:server` step so reviewers can reproduce the result.
